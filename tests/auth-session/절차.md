# 계약 3B 화면 시험 절차 — 테스트룸 인증 모듈·새 로그인 스위치 (브레인방이 시험 프로젝트를 상대로 돌린다)

- 대상: 시험 프로젝트 `hmncdheiwqwekdbtijar` **만**. 운영 `qpqjevecjejvbeuogtbx` 에는 어떤 요청도 보내지 않는다.
- 작업방은 이 절차를 돌리지 않았다. 작업방이 돌린 것은 가짜 서버 상대(`run.mjs`, `screen.mjs --fake`)뿐이다 — 실제 서버에서 된다는 증거가 아니다.
- 판정은 둘로 따로 낸다: 작업방의 가짜 요청 대조(회귀시험)와 이 절차의 실제 화면·실제 DB 대조. 앞의 것만으로 인수하지 않는다.
- SQL 파일(`sql/`)은 작업방이 실행해 보지 않았다(문법 확인도 못 했다). 열의 이름·형은 2026-11-21 의 구조 목록에서 읽었다.

## 0. 먼저 읽을 것 — 실행 전에 브레인방이 정해야 하는 것
1. **신청서 표의 트리거 셋**(`applications_protect_resume_approval_fields`·`applications_start_notice`·`applications_sync_correction_schedule`)의 함수 본문을 읽는다. 합성 신청서를 넣을 때(insert), 옛 길이 `self_paced_schedule` 을 고칠 때(update), 되돌릴 때(update), 지울 때(delete) 이 트리거들이 **바깥으로 알림을 보내거나 다른 표에 행을 만드는지**. 만든다면 이 절차를 그대로 돌리지 않는다(작업방에 알린다). 확인했으면 `fixtures_up.sql` 에 `set b3b.app_triggers_reviewed = 'yes';` 를 준다.
2. `fixtures_up.sql` 은 3-0 과 같은 방식으로 "파일 객체(`storage.objects`)가 0개"를 운영이 아니라는 증거로 본다. 시험 프로젝트에 객체가 남아 있으면 멈춘다.
3. 로그인 기록의 만료·되돌리기(`EX`)와 점검 켜기·끄기(`MT`)는 3-0 의 SQL(공홈 브랜치 `보안작업-묶음2-본인정보` 의 `supabase/tests/b3_0_my_profile/session_expire.sql`·`session_restore.sql`·`maint_on.sql`·`maint_off.sql`·`state_snapshot.sql`)을 3A 때와 같은 방식으로 쓴다.

### 1-2. 합성 자료 올리기 — `sql/fixtures_up.sql`

- 결과(한 칸 JSON)를 저장한다: `students`(실행기에 준다), `down_input`(되돌리기·내리기에 그대로 넘긴다), `counts`(회원 14·대응 14·신청서 15·학습 기록 66·마감 연장 1·tr_user_map 1).
- 날짜는 실행하는 날 기준이다(시작일 = 이번 주 일요일의 2주 전). **올린 날과 다른 주에 실행하면 "밀린 것·앞날"의 구성이 달라진다** — 같은 날 올리고 돌린다.

## 2. 실행
```
node tests/auth-session/screen.mjs --real --out <결과.json>
```
실행기가 로컬 서버 둘(켜짐·꺼짐 — 둘 다 시험 프로젝트의 주소·공개 키로 바꾼 사본을 내준다. 운영 값이 남은 파일은 내주지 않는다)과 제어 포트를 띄우고, 실제 Chromium 으로 경우 24개를 돈다. 경우마다 디스크에 남지 않는 새 브라우저 상태다.

- **모든 요청은 차단기를 거친 뒤에만 나간다.** 브라우저는 `127.0.0.1` 말고는 이름을 풀지 못하고, 시험 프로젝트로 가는 요청은 실행기가 대신 내보낸다. Sentry·첨삭 발주 웹훅·바깥 링크·소리 파일 등은 전송 전에 막힌다(경우마다 `outsideAttempts` 에 수가 적힌다).
- **P(차단의 예행)가 전부 참일 때만 뒤의 경우를 시작한다.** 비밀번호·이메일은 보관함에 있고 P 가 통과하기 전에는 꺼낼 수 없다. `--only` 를 줘도 P 는 먼저 돈다.
- **꺼짐의 화면(옛 길)이 보내는 요청도 전송 전에 좁힌다**: 회원 표 조회는 옛 길의 정확한 두 조회(합성 이메일로, 정해진 열 목록 / `password` 한 열)만, 신청서 조회는 합성 이메일·합성 번호로 좁힌 것만, 쓰기는 옛 길의 세 가지를 이번 실행의 합성 행·허용한 열로 보낼 때만. 그 밖의 쓰기·저장소 올리기·함수·다른 RPC 는 보내지 않는다. 합성 자료의 목록(`fixtures` 멈춤)을 받기 전에는 회원 표 조회·쓰기를 전부 막는다. 회원 표 조회의 응답 본문은 기록하지 않는다.

### 2-1. 제어 포트
`127.0.0.1:<포트>`. 머리글 `x-b3b-secret: <B3B_CONTROL_SECRET>` 이 맞는 요청만 받는다.
- `GET /wait` → `{ waiting: { step, kind, info, needsRevert } | null, pendingRevert }`
- `POST /continue?step=<단계 번호>` + 본문(JSON, 없을 수 있음) → 그 멈춤을 푼다. 단계 번호는 멈춤마다 새로 나오는 일회용이다.
- 기다림의 상한은 10분(`--pause-timeout-ms`). 넘으면 그 경우는 "미확인"이다.

### 2-2. 멈춤마다 브레인방이 할 일
| 멈춤(`kind`) | 경우 | `info` | 할 일 | 본문 |
|---|---|---|---|---|
| `fixtures` | F | `students`(유형 이름들) | `fixtures_up.sql` 결과의 `students` 를 준다 | `{"students":{…}}` — 유형마다 `memberId`·`appIds`·`recordIds` 만 |
| `old-path-begin` ⚠ | S-유형 | `student` | `sql/state_rows.sql` 로 지금 상태를 읽어 둔다(`changes` 가 빈 목록이어야 한다) | 없음 |
| `old-path-reset` | S-유형 | `student` | ① `state_rows.sql` 을 읽어 **옛 길의 실제 DB 변화**(`changes`)를 적어 둔다. `others` 의 `…_rest_changed` 가 0 인지(비대상 칸 불변), 행 수가 기대와 같은지 본다 ② `fixtures_reset.sql`(`check` → `apply`)로 되돌린다 ③ `state_rows.sql` 로 `changes` 가 다시 빈 목록인지 본다 | `{"reverted":true}` |
| `compare-plan` | S-유형 | `student`, `plan`(새 길의 저장 계획 — 실행기가 표·열·행·값을 검사하고 다시 만든 것) | ① `plan` 을 위 ①의 `changes` 와 **항목마다** 견준다(표·`match`·값. tr_user_map 의 `updated_at` 은 그때의 시각이라 있음만 본다) ② `state_rows.sql` 을 다시 읽어 **새 길 뒤 `changes` 가 빈 목록**이고 `others` 가 그대로인지 본다(세 업무 표의 대상 행·비대상 행 불변) | `{"result":"ok"\|"differs","unchanged":true\|false}` |
| `check-logout` | LO | `ended`(로그인 기록 번호) | 그 로그인 기록만 사라졌는지 DB 에서 본다 | `{"result":"ok"\|"differs"}` |
| `expire-session` ⚠ | EX | `sid` | 그 로그인 기록을 만료시킨다(3A 와 같은 방식) | 없음 |
| `restore-session` | EX | `sid` | 되돌리고 DB 에서 직접 대조한다 | `{"reverted":true}` |
| `maintenance-on` ⚠ | MT | `exception: fast` | 점검을 켜고 `fast` 의 계정을 예외 명단에 넣는다 | 없음 |
| `maintenance-off` | MT | | 끄고 DB 에서 직접 대조한다 | `{"reverted":true}` |
| `revert-confirm` | (원복 대상이 남았을 때) | `of` | 그 멈춤의 변경을 되돌리고 대조한다 | `{"reverted":true}` |

- **⚠ 표시가 있는 멈춤은 DB 변경이 남는다. 실행기는 그 멈춤을 내놓는 순간 "원복 대상"으로 표시한다**(답을 받았는지와 무관). 표시는 되돌리는 멈춤 또는 `revert-confirm` 에 `{"reverted":true}` 를 받아야 지워진다. 표시가 남아 있으면 다음 경우를 시작하지 않고, 끝내 받지 못하면 전체를 멈춘다(종료 코드 3, 결과의 `pendingRevert`).
- **저장 계획은 화면에서 온 값이다.** 실행기가 먼저 검사한다(표가 허용한 셋인가, 열이 허용한 열인가, 행이 이번 사례의 합성 행인가, 값의 모양이 정해 둔 형식인가). 벗어나면 넘기지 않고 그 경우는 "기대와 다름"이다(`notes.planRefused`). **계획을 SQL 로 실행하지 않는다** — 견주기만 한다.
- 유형 14개 × 멈춤 3개 = 42번의 멈춤이 있다. 도우미로 돌릴 때에도 `old-path-reset` 의 되돌리기는 `check` 의 결과를 본 뒤에 `apply` 한다.

## 5. 끝내기
1. `sql/state_rows.sql` 로 `changes` 가 빈 목록인지 본다(아니면 `fixtures_reset.sql`).
2. `sql/fixtures_down.sql`(넣은 수 = 지운 수, 남은 수 0).
3. 합성 로그인 계정 14개를 만든 번호 그대로 지운다. 실행 중 생긴 로그인 기록도 함께 사라지는지 본다.
4. 3-0·3A 와 같은 지문·수 대조로 시작과 끝이 같은지 본다.

## 6. 이 실행기로 확인되지 않는 것
- **탭 복제·닫은 탭 복원은 흉내다**(브라우저의 "탭 복제" 명령은 자동화로 부를 수 없다). 실행기는 `window.open` 으로 연 창(탭 단위 저장값이 복사된다)의 이름을 연 창과 같게 맞추고 연 창과의 연결을 끊어 복제된 탭의 조건을 만든다. 실제 브라우저의 탭 복제가 창 이름·탭 단위 저장값을 어떻게 다루는지는 손으로 봐야 한다.
- 모듈을 싣지 않는 화면(마이페이지 등)에 있는 동안 복제된 탭은 **먼저 첫 화면으로 돌아온 쪽**이 로그인을 이어받는다(다른 쪽은 로그인 화면). 어느 쪽이 "원래 탭"인지는 가릴 수 없다 — 갱신하는 창이 하나라는 것까지만 본다.
- 켜진 화면을 새로 고칠 때, 인증 모듈이 실리기 전(화면을 읽는 도중)에는 탭 단위 저장소에 앞의 `currentUser` 가 남아 있다(`notes.userPresentWhileLoading`). 실행기는 화면을 다 읽은 뒤부터를 잰다.
- 책 연결 주소(`auth_token`)·책 전용 상태는 이 실행기에서 돌리지 않는다(차단기가 책 연결의 회원 표 조회를 내보내지 않는다). 회귀시험(가짜)만 봤다.
- 실제 60분 자동 갱신, 가려진 탭, 휴대폰 브라우저. 두 탭의 갱신 충돌은 "복사된 값을 쓰지 않음"으로만 봤다.
- 일정 화면이 뜬 뒤의 업무 화면(과제·답안 저장·올리기) — 이 조각의 대상이 아니다. 답안 카드 창은 열어서 복사된 `currentUser` 를 읽는 것까지만 본다(제출하지 않는다).
- 회원 요청을 실제 브라우저가 직접 보내는 것(연결은 실행기가 맺는다). 허용 목록의 정적 자원을 받지 않고 그린 화면이다.
- 운영에서의 동작. 저장소의 스위치는 꺼짐이고 이 코드는 작업 브랜치에만 있다.
